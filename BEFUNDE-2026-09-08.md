# Befunde aus DruckerHub SPEC-0005, SPEC-0002 und SPEC-0003 (Stand 2026-09-09)

Gefunden bei drei vollständigen Durchläufen `sdd spec review` → Gate → TDD →
`sdd finalize` im Projekt `borisbrue/druckerhub`. Noch **nicht** als Issues
angelegt.

Sortiert nach Schwere. Behoben und deshalb entfernt: der Widerspruch zwischen
CLAUDE.md und `sdd init --help` zum `--autonomous`-Default; die Laufzeitausgabe
von `sdd start`, die auf `sdd dev exec` verwies (verweist jetzt korrekt auf
`sdd finalize`).

---

## 1. Der Dev-Container überschreibt das `.venv` des Hosts

**Schwere:** hoch — trifft jedes Projekt mit venv im Repo-Wurzelverzeichnis.

`dev_container.py` mountet `{root}:/workspace`. Legt im Container irgendein Befehl
ein venv an — `uv run` tut das ungefragt —, landet es unter `/workspace/.venv`,
also im bind-gemounteten Verzeichnis des Hosts. Danach zeigt `.venv/bin/python`
auf `/usr/local/bin/python3`, das es nur im Container gibt; auf dem Host läuft
nichts mehr, bis das venv neu gebaut ist.

Aufgetreten bei `sdd finalize SPEC-0005`: der Testlauf im Container ersetzte das
Python 3.13 des Hosts durch das 3.12 des Images, und `finalize` meldete daraufhin
"Tests fehlgeschlagen" — ein Infrastrukturproblem, das als Testfehler erschien.

**Vorschlag:** im Blueprint-Dockerfile `UV_PROJECT_ENVIRONMENT` auf einen Pfad
außerhalb von `/workspace` setzen, oder beim `run_container` ein anonymes Volume
auf `/workspace/.venv` legen, das den Mount überdeckt.

Im Projekt umgangen (`druckerhub@85f549f`), danach über zwei `finalize`-Läufe
bestätigt, dass das Host-venv unangetastet bleibt.

## 2. Ein übersprungener Check gilt als bestandener Check

**Schwere:** hoch — ein stiller Skip ist schlimmer als ein lautes Scheitern.

Zwei Ausprägungen desselben Musters:

**Pre-Commit-Gate.** Der Blueprint-Default ist `test_runner.command: pytest`.
`_resolve_runner` probiert `sys.executable -m pytest` (der Interpreter, der `sdd`
ausführt — hat pytest in der Regel nicht) und `shutil.which("pytest")` (nicht im
PATH ohne aktiviertes venv, der Normalfall bei uv-Projekten). Ergebnis:

    [sdd pre-commit] SPEC-0001 uebersprungen: Kein lauffaehiger Test-Runner
    gefunden (konfiguriert: 'pytest').

…und der Commit geht durch. Die Regressionsprüfung fällt aus, ohne dass jemand
etwas dagegen tun muss.

**Regression-Check.** Beim zweiten Lauf von `sdd spec regression SPEC-0002`:

    ⚠ LLM-Check übersprungen (claude CLI Timeout nach 120s.)
    ✓ Gate-Phase regression-ok markiert

Die Phase gilt als erfüllt, obwohl Stufe 2 gar nicht lief. Der erste Lauf
derselben Spec hatte zwei Widersprüche mit Severity ERROR gefunden — beide echt.
Wer den Check ein zweites Mal startet, kommt also durch, ohne dass sich etwas
geändert hätte.

**Vorschlag:** ein übersprungener Check markiert die Phase nicht als erfüllt,
sondern verlangt eine ausdrückliche Bestätigung. Beim Test-Runner zusätzlich ein
venv-bewusster Default.

Im Projekt umgangen: `uv run --no-sync pytest`. Das `--no-sync` ist Pflicht,
sonst greift Befund 1.

## 3. `finalize` pusht den Branch nicht, den es für den PR braucht

**Schwere:** mittel — der PR entsteht nie automatisch.

`sdd finalize SPEC-0002` legt `feat/SPEC-0002` lokal an, committet dorthin und
ruft dann `gh pr create`:

    pull request create failed: GraphQL: Head sha can't be blank,
    No commits between main and feat/SPEC-0002,
    Head ref must be a branch (createPullRequest)

Der Branch existiert auf `origin` nicht. Der PR landet als lokale Datei, und der
eigentliche Zweck des Kommandos — Spec → PR ohne Handgriffe — ist verfehlt.
Verwandt mit dem früheren Branch-Mismatch (#31), aber nicht dasselbe.

**Vorschlag:** vor `gh pr create` ein `git push -u origin <branch>`.

## 4. Der Pre-Commit-Hook stuft zurück, was `finalize` gerade gesetzt hat

**Schwere:** mittel — der committete Status ist falsch, und zwar reproduzierbar.

`sdd finalize` setzt die Spec auf `implemented`. Der **nächste** Commit stuft sie
still zurück:

    [sdd pre-commit] SPEC-0005: implemented → review (Inhalt geändert)

und committet `status: review`. Der Hook vergleicht gegen einen Hash, den
`finalize` nicht aktualisiert. Erst wenn `.sdd/content-hashes.json` mitcommittet
ist, hält der Status.

Bei SPEC-0002 traf es zusätzlich alle drei **Contracts** auf einmal:

    [sdd pre-commit] CON-0004: approved → review (Inhalt geändert)
    [sdd pre-commit] CON-0006: approved → review (Inhalt geändert)
    [sdd pre-commit] CON-0005: approved → review (Inhalt geändert)

Danach verweigerte `sdd start SPEC-0002` mit "hat Status 'review' – erst
Execution Gate durchlaufen", obwohl das Gate bei 9/9 stand. In beiden Durchläufen
aufgetreten, jedes Mal mit demselben Handgriff zu beheben.

**Vorschlag:** wer den Status ändert, schreibt den Content-Hash mit.

## 5. Nach einem gescheiterten `finalize` gibt es keinen Weg zurück

**Schwere:** mittel — blockiert, bis man den Container von Hand nachbaut.

`sdd finalize` entfernt den Dev-Container, **bevor** es scheitern kann. Beim
zweiten Anlauf:

    ✗ Dev-Container nicht gefunden – starte ihn mit 'sdd start SPEC-0005'

`sdd start SPEC-0005` antwortet aber "SPEC-0005 ist bereits in-progress." und tut
nichts. `sdd dev` gibt es seit SPEC-0044 nicht mehr. Ausweg war nur, den Container
von Hand identisch nachzubauen:

    podman run -d --name sdd-dev-spec-0005 -v "$PWD:/workspace" \
      -e SPEC_ID=SPEC-0005 -e GIT_BRANCH=dev/SPEC-0005 \
      sdd-dev:latest tail -f /dev/null

**Vorschlag:** `sdd start` zieht einen fehlenden Container auch für eine
in-progress-Spec wieder hoch, oder `finalize` räumt erst nach Erfolg ab.

## 6. `sdd test generate` erzeugt für AsyncAPI genau einen Rumpf

**Schwere:** niedrig — aber irreführend, weil es nach Abdeckung aussieht.

Für CON-0012 (OpenAPI, 3 Pfade) entstanden 3 Rümpfe, für CON-0013 (Gherkin, 31
Szenarien) 31. Für CON-0006 (AsyncAPI, 3 Nachrichtenarten, 4 verbindliche
Zusagen) entstand **einer**:

    ✓ CON-0006: tests/contract/test_live_statusstrom.py (1 Tests)

Der Generator kann Nachrichten offenbar nicht so aufzählen wie Pfade oder
Szenarien. Wer sich auf die Zahl verlässt, hält ein Protokoll für abgedeckt, das
mit einem einzigen `pytest.skip` ausgeliefert würde.

## 9. Fester PWA-Token im Blueprint

**Schwere:** niedrig heute, unsauber grundsätzlich.

`tool/sdd_cli/blueprint/config.yaml:164` enthält

    pwa:
      auth:
        token: 145df2f2…3e10

als Literal. `sdd init` kopiert ihn unverändert, und `.sdd/config.yaml` ist
versioniert — jedes so erzeugte Projekt trägt denselben 32-Byte-Wert in seiner
Historie. Gelesen wird der Schlüssel derzeit von keiner Codestelle (keine
Fundstelle in `tool/` außer dem Blueprint selbst), der Schaden ist also heute
theoretisch.

**Vorschlag:** bei `sdd init` erzeugen statt kopieren, oder den toten Schlüssel
entfernen.

## 10. Regression-Findings bekommen doppelte IDs

**Schwere:** mittel — Auflösungen landen am falschen Konflikt.

Jeder Lauf von `sdd spec regression` nummeriert seine Findings neu ab `R001`,
statt an den vorhandenen weiterzuzählen. Nach drei Läufen stand in
`.sdd/conflict-reports/SPEC-0003-conflicts.json` zweimal `CF-0003-R001` mit
**verschiedenem Inhalt**:

    CF-0003-R001 | resolved | FR-19 definiert Veraltung als 'mehr als zwei…
    CF-0003-R001 | open     | SPEC-0002 hält die Slicer-Schätzung je Dateiname…

`sdd conflict resolve SPEC-0003 CF-0003-R001` trifft die erste Fundstelle. Die
zweite bleibt offen und ist über die CLI nicht mehr erreichbar; schlimmer noch,
die Begründung für den einen Konflikt überschreibt die des anderen. Ich musste
den Bericht am Ende von Hand nach Inhalt zuordnen.

**Vorschlag:** fortlaufend nummerieren, oder einen bereits vorhandenen Befund
gleichen Inhalts aktualisieren statt neu anzulegen.

## 11. Querverweise auf fremde FRs gelten als eigene Anforderungen

**Schwere:** mittel — blockiert `sdd spec approve` mit einem Phantom.

`sdd spec approve SPEC-0003` brach ab mit:

    ✗ FR-24 hat keinen zugeordneten Test

SPEC-0003 hat 23 Anforderungen. Die FR-24 stammte aus einem Satz **im Fließtext**:
„Seit SPEC-0002 FR-24 gibt es zwei Intervalle." Der Konsistenzcheck sucht offenbar
nach `FR-\d+` im gesamten Dokument und zählt jede Nennung als eigene Anforderung.

Damit ist jeder Verweis auf eine fremde Spec ein Fehler — obwohl genau solche
Verweise das sind, was ein Regression-Check einfordert. Betroffen waren auch
SPEC-0001 und SPEC-0002, wo ich Verfeinerungen aus Nachbarspecs vermerkt hatte;
beide fielen dadurch aus `implemented` heraus. Behelf: alle Querverweise ohne
Nummer formulieren, was die Nachvollziehbarkeit kostet.

**Vorschlag:** nur `**FR-NN:**` am Zeilenanfang als eigene Anforderung werten, oder
Nennungen mit vorangehendem `SPEC-NNNN` ausnehmen.

## 12. `sdd start` zweigt immer von `main` ab

**Schwere:** mittel — der Framework-Pfad ist bei aufeinander aufbauenden Specs nicht gangbar.

`dev_container.py` ruft fest `git checkout -b dev/<SPEC> main`. Steht die Arbeit
einer noch nicht gemergten Vorgänger-Spec auf einem Feature-Branch, entsteht der
Entwicklungszweig ohne sie. Bei SPEC-0003 kam hinzu, dass `sdd start` an
uncommitteten Änderungen scheiterte, die es selbst erzeugt hatte (Spec-Status,
`audit.log`):

    Bitte committen oder stashen Sie Ihre Änderungen, bevor Sie Branches wechseln.
    ✗ Runtime-Fehler – Rollback abgeschlossen

Danach fehlt der Container, und `sdd finalize` verweigert (siehe Befund 5). Ich
habe die Containerprüfung deshalb von Hand gefahren.

**Vorschlag:** vom aktuellen HEAD abzweigen statt von `main`, und die eigenen
Änderungen vor dem Branchwechsel committen.
